# PriorityLab — Explainable Email Importance Classifier

> **A beginner-friendly, CPU-first Data Science × ML Engineering portfolio project**  
> **Status:** specification + microteaching deck ready; implementation starts at **Milestone 0** (setup → import data → EDA).  
> **Method:** CRISP-DM · **Audience:** grade-10 STEM mentorship · **Language:** English · **Date:** 18 November 2026

**Research question:** *How does Gmail flag important emails, and can we build a transparent, text-only approximation that other applications can consume through an API?*

**Important distinction:** Gmail's importance marker uses multiple signals, including a user's behavior. Our model deliberately uses **only email subject and body**. It is an independent educational prototype, **not a replica of Google's algorithm**, and **does not predict personalized importance**.

## 1. What we'll build

A **binary email importance classifier** that returns `important` or `not_important`, plus an explanation of what contributed to the prediction.

```text
                    DATA SCIENCE                                    ML ENGINEERING
[Synthetic emails] → [EDA + cleaning] → [features] → [classifier] → [Saved pipeline]
                                                                        |
[Other app / service] → POST /v1/predict → [FastAPI service] ───────────┘
                                               |
                                    JSON: flag + model evidence
```

**Milestone 1 features:** TF-IDF + Logistic Regression (lexical evidence).  
**Milestone 2 features:** frozen sentence embeddings (`all-MiniLM-L6-v2`) + Logistic Regression (semantic vectors), compared against the TF-IDF baseline.  
**Core stack:** Python, Hugging Face Datasets, pandas, matplotlib, scikit-learn, joblib, FastAPI, Pydantic, pytest. M2 adds `sentence-transformers`. **No paid API, LLM training, Gmail access, or production infrastructure needed.**

## 2. Motivation: what Google publicly says vs. what we can model

[Google's Gmail Help](https://support.google.com/mail/answer/186543?hl=en) says importance markers may consider:
- Who you email and how often.
- Which emails you open or reply to.
- Words in emails you normally read.
- Star, archive, and delete actions.

Our open synthetic dataset has **no per-user interaction history**. The MVP therefore learns **generic, content-derived priority**, not individualized Gmail importance.

| Capability | Gmail publicly documented | PriorityLab MVP |
|---|---|---|
| Read email content signals | Yes | **Yes**: subject + body |
| Use sender/interaction history | Yes | **No** |
| Adapt to different users | Part of Gmail's design | **Explicitly out of scope** |
| Show important/not-important marker | Yes | **Yes**: our own modeled proxy |
| Predict action (reply/archive/forward) | Different task | **No** |

The phrase *"how Gmail works"* in the presentation is the **domain motivation**; our project does not claim to know Google's internal architecture or train on Gmail labels.

## 3. Dataset and target

**Source:** [weijianzhg/email-triage-action-seed](https://huggingface.co/datasets/weijianzhg/email-triage-action-seed)  
**Dataset card:** 3,905 **synthetic** English-language email examples, Apache-2.0, one published `train` split.

| Field | Role in our project |
|---|---|
| `subject` | Model input |
| `body` | Model input |
| `priority` | **Source label**, to be mapped to a binary target |
| `category` | EDA only (not an input) |
| `action` | EDA only (not an input, not predicted) |
| `source_round` | Dataset provenance / leakage audit only |

**Provisional, documented label mapping** (subject to dataset audit):

| Source priority | Binary target |
|---|---|
| `urgent`, `high` | `important` (`1`) |
| `medium`, `low` | `not_important` (`0`) |

This mapping is **our modeling assumption**, not a native label in the dataset and not Gmail's definition of importance. The dataset card describes four allowed priority values, while the current viewer shows only **three represented values**; verify the actual set and class balance in EDA before training. **Stop if either binary class is absent.**

**Limitations:** data were generated by one LLM, have a narrow writing style, use only English and contain no human judgment of importance. A high offline score on synthetic examples does not demonstrate generalization to a real inbox.

## 4. CRISP-DM end-to-end plan

| Phase | Main question | Output | Status |
|---|---|---|---|
| 1. **Business understanding** | What is important? What would success look like? | scope, label rubric, risk and metrics | **Specified** |
| 2. **Data understanding** | What's in the corpus? How reliable are labels? | EDA charts, distributions, bias audit | **Next (M0)** |
| 3. **Data preparation** | How to split without leakage? | clean subject+body, dedup, reproducible split | Planned |
| 4. **Modeling** | Can a simple model learn useful signals? | Dummy → TF-IDF+LogReg (M1); embeddings+LogReg (M2) | Planned |
| 5. **Evaluation** | When and why does it fail? | confusion matrix, macro F1, important recall, explanations | Planned |
| 6. **Deployment** | Can another service request a prediction? | saved pipeline + tested FastAPI endpoint | Planned (M3) |

**Fundamental concepts (M1):** labels and features; train vs. test; Bag-of-Words → TF-IDF; linear classifier weights; false positives/false negatives; explainability; training vs. inference; REST API.  
**Advanced concept (M2):** pretrained sentence encoder → dense meaning vector → linear head (encoder frozen).

**Engineering rule:** fit feature extractors **only on training data**. `category`, `action` and `source_round` must not enter the model's feature text. Inspect duplicate/near-duplicate generated emails before splitting.

```json
  "is_important": true,

```

> **Illustrative response only** — no model has been trained. For M1, `top_terms` come from TF-IDF/classifier weights. For M2, lexical `top_terms` may be empty or replaced with a different evidence field — keep the same endpoint shape where possible. Scores must not be presented as calibrated confidence without testing.

## 8. Microteaching — 15 minutes, 1-on-1

**Teaching order:** motivation → CRISP-DM → **milestones (M0–M3)** → email domain → Bag of Words → practice → **TF-IDF (TF × IDF)** → **Logistic Regression steps** → hard cases → **M0 setup guide**.

| Block | Mentor activity | Student participation |
|---|---|---|
| Hook | Pick which of 2 emails deserves attention | Choose + explain |
| Lifecycle | Explain CRISP-DM | See train vs. deploy |
| Roadmap | Show M0→M3 milestones | Know what comes first |
| Domain | Gmail signals vs. text-only scope | Notice missing signals |
| BoW → TF-IDF | Counts, then TF × IDF weighting | Build a BoW vector |
| LogReg | Feature × weight → score → probability → label | Separate vectorizer vs classifier |
| Challenge | `URGENT SALE` vs real deadline | Spot keyword traps |
| Wrap-up | Walk M0 setup steps + learning links | Start GitHub / env / import / EDA |

**Student next step:** follow Milestone 0 — create/push the GitHub repo, set up a Python env, import the Hugging Face dataset, and begin EDA. Learning links are in §9 below.
